一、Skills vs 提示词 vs MCP

这三个概念经常被混淆，我用一个表格帮你理清：

  • 提示词 = 口头交代任务，说完就忘。对应的是一次性任务
  • Skills = 员工手册，随时可查。对应重复性任务和固定规范
  • MCP = 给员工配的工具（浏览器、数据库访问权限等）。需要访问外部数据时使用

三者不是互斥的。实际工作中，可能用 Skills 定义代码规范，用 MCP 连接数据库，再用 提示词 说「帮我查一下用户表里上周的新增数据」。

二、Skill 的原理

在讲应用场景之前，先搞清楚 Skill 是怎么工作的。

一个完整的 Skill 包含下面文件

其中 SKILL.md 是唯一必须的文件，其他都是按需添加。

Claude 加载 Skill 的过程：

  • 发现阶段：Claude 启动时扫描所有 Skill 目录，只读取每个 SKILL.md description 字段
  • 匹配阶段：用户输入后，Claude 根据 description 判断是否需要某个 Skill
  • 加载阶段：如果匹配，Claude 读取完整的 SKILL.md 内容
  • 执行阶段：按照 Skill 中的指引处理任务，必要时调用 scripts/ 里的脚本

Skill 不会一直占用上下文窗口。只有 description 会常驻内存（很短），完整内容只在需要时加载。这是 Skill 比「超长系统提示词」高效的关键原因。

Skill 的几个核心特性

  • 自动触发：不需要手动调用，Claude 根据任务自动识别
  • 可组合：多个 Skill 可以在同一任务中协作
  • 可扩展：通过 scripts/ 和 references/ 扩展能力
  • 版本化：放在 Git 里可以追踪变更

Skill 可以放在三个地方，优先级从高到低：

项目目录.claude/skills/

  • 适合：项目特定的规范、工作流
  • 优点：跟项目代码一起版本控制，团队共享

用户目录 ~/.claude/skills/

  • 适合：个人通用的 Skill
  • 优点：所有项目都能用

插件目录（由工具自动管理）

  • 适合：第三方 Skill 包
  • 例如：通过包管理器安装的社区 Skill

除非有明确的项目特定需求，否则都放 ~/.claude/skills/ 。放一个地方好管理，不容易忘记自己有哪些 Skill。

三、Skill 的创建

创建 Skill 的核心其实很简单：写一个 SKILL.md 文件，放到对应目录就行。

但要让 Skill 真正好用，还需要理解脚本、参考文件和迭代优化。

my-skill/
├── SKILL.md          # 核心文件，必须有
├── references/       # 参考文档（可选）
│   ├── api-docs.md
│   └── examples.md
├── scripts/          # 可执行脚本（可选）
│   ├── generate.py
│   └── validate.sh
└── templates/        # 模板文件（可选）
    └── output.md

创建 Skill 前，先调整一下心态： 要胆大 。

把 Claude Code 想象成一个无所不能的程序员、一个电脑高手，它能交付你任何任务。任何你日常重复做的事情，任何你有固定套路的工作，都可以尝试做成 Skill。

在开始创建之前，确保完成以下准备：

1. 安装并配置好 Claude Code

如果还没装，可以参考 claude code 小白级安装指南和必备工具

2. 下载 skill-creator

这是官方提供的 Skill 创建向导，地址：

https://github.com/anthropics/skills/tree/main/skills/skill-creator

下载后放到 ~/.claude/skills/ 目录即可。有了它，Claude 就能引导你一步步创建 Skill。

3.1 方法一：把提示词做成 Skill

这是最快的方式。你肯定收藏过一些好用的提示词，与其每次复制粘贴，不如直接做成 Skill。

案例：审稿员提示词

假设你有这样一个提示词：

3. 共鸣：写的东西读者是不是也经历过同样的痛苦、困境？
4.人设： 始终围绕着 AI 创业者【你自己的人设】的身份来写
5. 干货：读者是否有获得感？信息增益？
6. 好玩： case 是否好玩？ 这是流量基础
8. 对话感：好内容语气应该是跟读者对话 让读者忍不住在评论区里回复

操作步骤：

  • 打开 Claude Code
  • 把提示词贴进去，然后说：「 根据这个提示词创建一个 Skill 」
  • Claude 会问你几个问题：
  • Claude 生成 SKILL.md，保存到 ~/.claude/skills/article-reviewer/

以后你只需要说「 帮我审一下这篇文章 」，Claude 就自动调用 Skill 来审稿。

3.2 方法二：描述 SOP 创建 Skill

如果你没有现成的提示词，但有一套固定的工作流程（SOP），也可以直接描述给 Claude，让它帮你做成 Skill。

有哪些 SOP 适合做成 Skill？

  • 写作 SOP：写公众号文章的固定流程
  • 会议 SOP：整理会议纪要的模板和步骤
  • 审批 SOP：处理各类申请的检查清单
  • 复盘 SOP：项目复盘的固定框架
  • ......

案例：写作 SOP 变成 Skill

假设你写公众号文章有这样一套流程：

  • 先确定选题和核心观点
  • 列出 3-5 个大纲选项
  • 选定大纲后逐段展开
  • 写完后检查：标题是否吸引人、开头是否有 hook、结尾是否有行动号召
  • 最后润色语言风格

操作步骤：

  • 打开 Claude Code，说：
帮我创建一个写公众号文章的 Skill。
我的写作流程是：
1. 先确定选题和核心观点
2. 列出 3-5 个大纲选项让我选
3. 选定后逐段展开
4. 写完检查标题、开头 hook、结尾 CTA
5. 润色成我喜欢的风格：干货但轻松，像朋友聊天

Claude 会追问细节，比如「你平时写什么类型的文章」「有没有参考样本」

回答完后，它会生成完整的 SKILL.md

如何写好 SOP 描述？

  • 写清楚每一步要做什么
  • 说明每一步的输入和输出
  • 提供你喜欢的风格或样本
  • 说明哪些情况需要特殊处理

3.4 什么时候需要脚本文件

SKILL.md 只能提供「知识」，但有些任务需要「能力」——这时候就需要脚本。

需要脚本的场景：

  • 文件格式转换（PDF → Markdown、Excel → JSON）
  • 数据处理（批量重命名、格式化）
  • 调用外部 API（天气、翻译、搜索）
  • 执行验证逻辑（检查文件是否符合规范）
  • ...

3.5 如何创建脚本

建脚本也不需要自己手动去写代码，但你需要有一个 意识 ：知道你的 Skill 是否需要依赖脚本。

脚本就是一段可以被执行的代码。当 Claude 遇到它自己做不了的事（比如访问网络、操作文件系统、调用外部 API），它就会运行脚本来完成。

脚本的类型：

  • Python 脚本 （.py ）：最常用，适合数据处理、网络请求、文件转换
  • Shell 脚本 （.sh ）：适合系统操作、批量命令、环境配置
  • Node.js 脚本 （.js ）：适合前端相关、JSON 处理

案例：X（Twitter）内容抓取 Skill

假设你想创建一个 Skill，能够抓取 X 上某个用户的推文并保存到本地。这个任务 Claude 自己做不了（需要网络请求），所以需要脚本。

创建时这样描述：

帮我创建一个抓取 X 内容的 Skill。

功能：
1. 输入一个 X 用户的用户名
2. 抓取该用户最近 100 条推文
3. 保存为 Markdown 格式到指定目录

技术细节：
- 需要用 Python 写抓取脚本
- 保存位置：~/Documents/x-archives/
- 文件命名：用户名_日期.md

Claude 会帮你生成完整的 Skill，包括脚本文件。

生成的目录结构：

└── scripts/
    └── fetch_tweets.py    # Python 抓取脚本

脚本内容示例：

# Claude 会根据你的需求生成具体代码

    # 保存为 Markdown
    filename = f"{username}_{datetime.now().strftime('%Y%m%d')}.md"
    # ...

if __name__ == "__main__":
    username = sys.argv[1]
    output_dir = sys.argv[2]
    fetch_tweets(username, output_dir)

SKILL.md 中如何引用脚本：

python scripts/fetch_tweets.py <用户名> <保存目录>

参数说明：
- 用户名：X 的 @handle，不带 @
- 保存目录：默认为 ~/Documents/x-archives/

脚本会自动：
1. 请求 X API 获取推文
2. 格式化为 Markdown
3. 保存到指定位置

Claude 会读懂这些说明，在你说「帮我抓取 @elonmusk 的最近推文」时自动调用脚本。

创建脚本的关键：

你不需要自己写代码，告诉 Claude 你要做什么就行，获取什么数据，在描述 Skill 时说清楚：输入是什么、输出是什么、保存在哪里，Claude 会帮你生成脚本，你只需要确认能跑通。

如果脚本运行出错，直接把错误信息贴给 Claude，它会帮你修复。

3.6 如何使用参考文件

如果你要让 AI 参考你的风格输出文章

就可以放很多篇你自己写过的文章在在 references/ 目录

除了文章，其他适合做参考文件的内容：

  • API 文档（接口定义、参数说明）
  • 代码规范（团队的编码标准）
  • 术语表（专业词汇对照）
  • 示例文件（期望的输入输出样本）

SKILL.md 中如何引用参考文件：

- \`references/coding-style.md\`：代码规范
- \`references/examples/\`：示例代码目录

3.7 迭代优化 Skill

Skill 不是写完就完了。用着用着你会发现：有些场景没覆盖到，有些输出不够理想。

迭代流程：

  • 发现问题：用 Skill 执行任务，发现输出不满意
  • 让 AI 优化输出：直接告诉 Claude「这个输出不太对，帮我改成 XXX 风格」
  • 反向优化 Skill：对 Claude 说「根据刚才的改进，帮我更新 Skill 文件」
  • 测试验证：用新的 Skill 再跑一遍，看效果

实际例子：

你：「用写作助手帮我写篇产品介绍」
Claude：（输出了一篇文章）
你：「太正式了，我想要更口语化、更有网感的风格」
Claude：（重新输出）
你：「这个风格对了。把这个风格要求更新到 Skill 里」
Claude：（更新 SKILL.md，加入风格指引）

这样你的 Skill 会越用越贴合你的需求。

优化建议：

  • 每次发现问题就记录下来，攒几个一起更新
  • 好的输出可以存到 references/examples/ 作为样本

四、使用 Skill 与注意事项

4.1 存放位置的选择

前面提到 Skill 可以放项目目录或用户目录。我的建议是： 除非有明确理由，都放 ~/.claude/skills/ 。

原因很简单：

  • 放一个地方，不容易忘记自己有哪些 Skill
  • 跨项目通用，不需要每个项目都复制一份
  • 方便统一管理和更新

只有真正「项目特定」的 Skill 才放项目目录，比如某个项目独有的代码规范。

4.2 命名要理解

我用了一段时间Skill会发现： 最大的问题是忘了自己有哪个 Skill 。

我的 Skill 命名基本都是 AI 自动生成。

现在我会刻意记住这些名字，知道它代表什么技能。

并且避免 Skill 1 和 Skill2 的名字相似、重复。

因为AI 不会每次都自动调用Skill，S kill 不是 100% 自动触发的。

Claude 根据 description 判断是否需要某个 Skill。如果 description 写得不够精准，或者你的表述和 description 差太远，可能就不会触发。

建议建立自己的命名规范：

  • 按功能命名： pdf-extractor 、 email-writer
  • 按场景命名： morning-standup 、 weekly-report

如果忘记了 Skill 的名字：

  • 手动提醒：「用 XX Skill 帮我做这件事，名字我忘记了，但是它可以帮我 xxxx，你可以在 xx 目录找下」
  • 检查 Skill 是否被正确加载（Claude 会在触发时提示）
