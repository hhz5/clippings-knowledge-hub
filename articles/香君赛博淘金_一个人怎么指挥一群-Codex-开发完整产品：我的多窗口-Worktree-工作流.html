一个人怎么指挥一群 Codex 开发完整产品：我的多窗口 Worktree 工作流

香君赛博淘金 编程AICodexWorktree项目管理 2026-08-04

最近总有人问我一个问题：Vibe Coding 到底能不能行？它能不能不靠专业开发团队，真的出栏一个完整产品？

香君赛博淘金 香君赛博淘金 2026年8月4日 00:51

最近总有人问我一个问题：Vibe Coding 到底能不能行？它能不能不靠专业开发团队，真的出栏一个完整产品？

我先说结论：能，但你不能真的只靠 vibe。

如果你对 Vibe Coding 的理解是，坐在电脑前随口说一句“帮我做个 App”，然后等 AI 一次性把能上线的产品吐出来，那大概率只能得到一个看上去能跑的 Demo。首页能打开，按钮能点击，拿出去演示也挺像那么回事；但一接真实数据、一补异常状态、一换设备、一跑完整测试，问题就全出来了。

一个完整产品远不止页面和功能能跑。它还包括前端、后端、数据、状态、权限、隐私、测试、修复和最终集成。这里面有些事可以同时做，有些必须按顺序做，还有些做完以后必须交给另一个角色重新验收。

我最近就在用这套方式推进一个全栈桌面工具。项目名字和具体功能先不展开，只讲开发过程。回头看 Codex 左侧的任务列表，从底层约束、前后端、隐私和环境兼容，到后面的多套界面，拉下来一长串。整个项目被拆成多批任务，让多个 Codex 窗口分别在独立 Worktree 里推进，再一批一批合回来。

任务列表

这篇不准备写成保姆级教程，也不会把我的完整 Prompt、调度规则和验收标准贴出来。我主要想讲清楚一件事：一个人怎么把 Codex 从“帮我写代码的聊天框”，变成一支可以被组织、被隔离、被验收的小型开发队伍。

一、Vibe Coding 卡住的，往往不是代码能力

很多人判断 Vibe Coding 行不行，盯着的是模型会不会写代码。这个标准已经有点落后了。

现在的模型写一个页面、补一个接口、改一段逻辑，能力都不差。难点在于，一个完整项目不会只出现一个问题。它可能同时需要改数据结构、补后端命令、接前端状态、处理隐私边界、兼容不同客户端，再把测试跑通。

如果这些东西全塞进一个窗口，前几轮通常还好。聊得越来越长以后，问题就开始出现了。

最早定下来的约束被埋在几十轮对话里；前端的问题修着修着，Agent 又跑去重构后端；测试失败以后不断追加补丁，自己也说不清哪次修改造成了回归。更麻烦的是，一个窗口既负责设计、又负责实现、还负责证明自己实现得没问题，很容易自己给自己验收通过。

所以大项目做不下去，很多时候卡的不是 Codex 会不会写，而是我们还在用“一问一答”的方式管理一项本质上需要多人协作的工程。

我后来越来越明确：大任务要拆成多个边界清楚的小任务，分批推进、反复收口，不能靠一段无限延长的对话硬扛。

这里要把三个容易混在一起的概念分开。

多轮，是一个任务沿着时间往前走。先理解，再实现，再测试，再修正。

多窗口，是多个任务同时往前走。后端在补命令时，前端可以做已经冻结接口的页面，另一个窗口可以补测试。

Worktree，则是给每个窗口一套独立的代码现场。大家仍然在同一个项目里工作，但不会同时踩在同一份文件上。

一句话概括就是：

多窗口只是多了几双手，Worktree 才是给每双手分了一张独立工作台。

二、多开窗口，不等于并行开发

多窗口目录

很多人第一次发现 Codex 可以同时跑多个任务，第一反应就是：那我多开几个窗口，不就相当于多了几个程序员？

思路没错，但只对了一半。

假设你正在做一个产品，一个窗口改登录，一个窗口接支付，一个窗口重做首页。三个任务同时跑，看起来效率翻了三倍。可如果三个窗口都指向同一个项目目录，麻烦很快就来了。

这个窗口刚把公共组件重构完，另一个窗口还在按照旧结构继续写；一个窗口运行测试显示通过，另一个窗口刚好保存了一批文件，结果测试现场已经变了；更糟糕的时候，某个 Agent 看到目录里有一批自己没产生的改动，会顺手整理、覆盖甚至回退。

最后不是三个程序员在协作，而是三个人挤在同一张桌子上，同时改同一份稿子。

Worktree 解决的就是这个问题。Git 允许同一个仓库同时拥有多个工作目录，每个目录对应自己的分支和文件状态。放到 Codex 里理解，就是每个执行窗口进入自己的“独立工位”：它可以改代码、运行项目、做测试、提交结果，但不会直接弄乱其他窗口的现场。

OpenAI 在介绍 Codex App 时 [1] ，也把多 Agent 并行和内置 Worktree 支持放在了一起。原因很简单：没有隔离，多 Agent 带来的第一批东西很可能就是冲突。

但这里还有一个特别容易被误解的地方：Worktree 只能隔离文件，不能替你拆任务。

如果两个窗口都要修改同一个公共接口、同一个数据库结构或同一套核心状态，即使它们各自在不同 Worktree 里写得很开心，最后合并时照样会撞在一起。文件没有互相覆盖，不代表逻辑没有互相冲突。

正确顺序应该是：先看清依赖，确定任务边界，再决定哪些任务值得进入独立 Worktree。不要先建一堆 Worktree，再临时想每个窗口干什么。

三、真正的起点，是让主控 Agent 先拆 Spec 和 Task

我做这个项目时，没有先列十几个窗口再随手分任务。我先让一个主控 Agent 理解整个项目，把需求拆成 Spec，再从 Spec 里拆出 Task。

Spec 解决的是“我们到底要做什么”。目标是什么，边界在哪里，哪些旧东西要保留，哪些明确不做，最终以什么状态算完成。

Task 解决的是“这些工作按什么关系发生”。哪个任务依赖哪个任务，哪些会改公共部分，哪些只会动独立模块，哪些可以同时开工，哪些必须等上一批完成。

Spec 与 Task

这里最反直觉的一点是：

并行开发的第一步，不是找能并行的部分，而是先找出不能并行的部分。

像共享数据模型、前后端通信契约、核心状态结构，这些东西如果还在不停变化，后面的窗口开得越多，返工就越多。大家看起来都很忙，但每个人依赖的地基都在移动。

我的做法是，先让主控把公共边界收紧。等共享契约基本稳定，再把那些修改范围清楚、彼此依赖较弱的任务并发出去。

主控 Agent 在这里更像项目负责人，不是团队里写代码最多的人。它最重要的工作，是维护全局一致：谁先做，谁后做；谁可以动公共代码，谁只能待在自己的目录里；哪一批结束以后必须停下来集成，不能继续往前冲。

执行窗口则完全相反。它不需要天天重新思考整个产品，只需要把自己的局部任务做深：读清楚相关 Spec，在边界内实现，跑完应该跑的测试，然后把结果交回来。

主控负责全局，执行 Agent 负责局部。这两个角色一旦混在一起，多窗口很容易重新退化成“多个 Agent 各自理解了一个版本的产品”。

四、一个全栈项目，是怎么分批跑起来的

我选择的案例，是一个我正在开发着玩的工作平台。它不是一个单页 Demo，而是有前端、后端和桌面运行环境，还涉及数据安全、状态隔离以及不同环境之间的兼容。后面又增加了几个相互关联的功能模块和多套结构差异很大的完整界面。下面只保留对方法有用的信息，具体业务和功能细节都做了脱敏。

如果全交给一个 Codex 窗口按顺序做，当然也不是完全不能做，但周期会非常长。更大的问题是，上下文会越来越重。它刚处理完后端边界，又要记住前端交互细节，接着还要回头修跨模块流程，注意力会不停切换。

我最后采用的节奏，是让串行和并行交替发生，而不是一次性全部开跑。

第一批主要处理底层能力。共享契约、领域模型、运行边界、数据安全和环境兼容，这些任务之间有联系，但可以在边界确认后由不同窗口分别推进。

这一批做完以后先合回来，不马上开更多窗口继续加功能。合并除了处理 Git 冲突，还要检查不同 Agent 对同一个概念有没有理解偏差：前端和后端理解的数据是不是一回事，一个模块依赖的状态是否真的存在，安全约束有没有在另一条链路里被绕过去。

第一次集成稳定以后，第二批才开始做更靠近产品的前后端功能。后端能力、前端工作台、数据链路、任务流程、日志和异常状态，可以沿着已经明确的契约继续拆开。

这一轮特别能说明，前端和后端完全可以并行，前提是开工前约定好接口。如果接口没定，前端会先按自己的理解造一份数据，后端再按另一种格式返回。两边都完成了各自的任务，合起来却不能用，这不叫并行提速，叫并行返工。

第二批合并后，我又做了一轮真实链路和生产环境修正。很多 Demo 到产品的差距就藏在这里：假数据下能跑，接真实后端不一定能跑；开发窗口里能打开，生产构建不一定能打开；正常流程能完成，遇到中断、空状态和异常状态不一定能恢复。

到了第三批，公共行为层已经比较稳定，我才把三套完整界面方案同时拆出去。

这三套不是换个颜色，而是页面结构、信息密度和交互语言都不一样。每套都要覆盖同一批核心页面和业务状态。如果让一个窗口按顺序做，很容易做完第一套以后，后两套越来越像第一套的换皮。

这时 Worktree 的价值就特别直观。三个窗口分别挂在三个独立 Worktree 上，只负责自己的呈现模块。公共控制器、后端逻辑和状态管理已经冻结，不允许为了自己方便顺手重构。它们共享同一副骨架，但各自完成完整的视觉实现。

三套界面

同一套行为层上的三套完整界面。

三套完成后，再进入专门的集成 Worktree。这个阶段的重点不再是自由开发，而是合并、对齐和验收：三套界面是否都调用同一套真实行为，功能状态有没有遗漏，响应式有没有溢出，键盘操作能不能完成，生产构建是否正常。

视觉部分最后按多套界面、核心页面和不同尺寸生成了一批截图。这组截图是验收材料，强迫我们把“我觉得差不多”变成一组能被逐项检查的结果。

整个项目真正跑起来的节奏是：

主控拆解 → 串行打地基 → 第一批并发 → 集成 → 第二批并发 → 集成 → 第三批并发 → 最终验收。

不是所有窗口从第一天一起跑到最后，也不是某个 Agent 从头到尾包办一切。能并发的同时做，有依赖的排队做，每一批结束都必须重新收口。

五、什么任务适合放进独立 Worktree

我现在判断一个任务要不要并发，主要看它的边界稳不稳，任务大小反而排在后面。

一个任务如果主要修改自己的模块、自己的目录，输入输出已经明确，完成以后可以单独测试，就比较适合进入独立 Worktree。比如三套界面各自负责自己的呈现模块，就是很干净的并发任务。

前端和后端也可以并发，但前提是通信契约已经冻结。一个负责按约定提供数据，一个负责按约定消费数据，最后在集成阶段接起来。

测试、审查和文档也经常适合单独拆出去。尤其是审查，它和实现放在同一个上下文里，Agent 很容易沿着自己原来的思路继续证明自己正确。换一个干净窗口，反而更容易发现遗漏。

相反，如果产品目标还没想明白，公共数据结构还在频繁变化，几个任务都会抢着改同一套核心文件，这时候就不适合并发。还有一些跨全局的大重构，看起来能拆成很多小块，实际上每一块都依赖整体迁移顺序，硬拆只会让最终集成更痛苦。

所以并发不是越多越好。多开一个窗口，就多一份需要同步的理解、多一次需要验收的交付，也多一种潜在冲突。

这件事很像招人。公司不会因为人越多就自动效率越高，边界不清时，多一个人只是多一个沟通节点。Codex 窗口也是一样。

六、怎么防止一群 Codex 集体跑偏

单窗口跑偏，通常还能顺着对话拉回来。多窗口一起跑偏，最后会得到好几套看起来都说得通、但互相接不上的实现。

比起要求 Agent “更聪明”，我更在意减少它需要自由猜测的地方。

每个执行窗口都应该知道本轮只负责什么，不负责什么；依赖哪份已经确认的约定；哪些公共部分不能碰；完成以后要留下什么结果。这里不需要把整个项目重新塞给它，信息越多也不一定越好。一个干净上下文只保留完成当前任务真正需要的材料，反而更稳。

另一个常见问题，是任务中途不断追加。“这个也顺便改一下”“那里看着不舒服也一起处理”，人类觉得只是举手之劳，Agent 却可能因此越过原来的边界，开始修改其他 Worktree 也在依赖的公共代码。

我现在会尽量把“顺手改”当成危险信号。发现新问题可以记录，可以另开任务，但不要让当前窗口无限扩张。

每个执行窗口说“完成了”，也不代表真的完成。它至少要能说明改了什么、验证了什么、还有什么风险。结果回到集成阶段以后，还要重新测试。执行 Agent 的自我汇报是交接材料，不是最终验收结论。

这里还有一个我认为非常值钱的角色：专门做集成和验收的窗口。

很多人有空位时，第一反应是再开一个开发窗口，多做一个功能。但在多 Agent 项目里，一个不负责继续加功能、只负责检查合并结果的窗口，经常比多一个执行窗口更有价值。

因为并发会放大产出，也会放大偏差。没有收口机制，你只是更快地得到更多未经确认的代码。

七、Worktree 不是什么高深技术，真正的门槛是组织能力

Worktree 很重要，但它不是整套方法的主角。

它解决的是现场隔离：每个 Agent 有自己的目录、分支和修改记录，一个任务失败时，不会直接把其他任务的工作区搞乱。

它解决不了任务依赖，不会替你判断两个模块能不能同时改；解决不了产品理解，不会保证多个 Agent 对同一条需求的解释一致；也解决不了质量问题，不会因为代码来自独立 Worktree，就自动变成可上线的代码。

整套方法可以归成四个动作：拆、隔、并、收。

先拆。把产品拆成有边界、有依赖关系的任务。

再隔。给每个执行任务独立的代码现场和上下文。

再并。只让那些边界已经稳定的部分同时推进。

再收。每一批结束以后回到主线，统一集成、测试和验收。

这四步里，Worktree 主要负责“隔”。前面的“拆”和后面的“收”，才决定这套方法能跑到多大规模。

我不太认同把 Vibe Coding 简单分成“行”或者“不行”。如果所谓 Vibe Coding，是随口描述一个想法，把第一版生成结果直接当产品，那它当然很难做出真正能用的东西。

但如果 Vibe Coding 指的是，人负责目标、判断和验收，AI 负责大量分析、实现和修正；人不再亲手写每一行代码，而是组织多个 Agent 完成一个经过设计的开发流程，那它完全可以进入更复杂的产品开发。

只不过到了这个阶段，你的角色已经变了。

你不再只是一个向 AI 提需求的人。你同时在做产品负责人、项目经理、架构协调和质量验收。你不一定亲手完成每个模块，但你必须知道什么时候该拆、什么时候该停、什么时候能并发、什么时候必须把所有东西合回来重新检查。

这也是个人创业者用 Codex 最有意思的地方。过去一个人做产品，最大的瓶颈往往是执行带宽：想法很多，真正能同时推进的事情很少。现在多个 Agent 可以把执行带宽放大，但它没有消灭管理，反而把管理能力提前变成了瓶颈。

所以回到开头的问题：Vibe Coding 能不能做出一个完整产品？

我的答案是，可以。但靠的不是一条更神的 Prompt，也不是把窗口开得越多越好。

更有效的方式，是把一个复杂项目拆成多批任务，让一个主控 Agent 维持全局，让多个执行窗口在独立 Worktree 里把局部做深，再由集成窗口把结果一批批收回来。

一个人指挥一群 Codex，本质上不是在同时开很多聊天框，而是在经营一支小型软件团队。
