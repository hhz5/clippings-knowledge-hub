最近一直在想一个问题：为什么同样的 AI 工具，有人能用它做出完整的产品，有人用两次就放弃了。

举 个 例 子：

让一个经验丰富的开发和一个技术小白，同样用 Agent 去描述"怎么做一个剪辑工具"。

小白可能会说：我要做一个剪辑工具。然后...就没了。好一点的，会描述一下界面上有哪些按钮。

但一个有经验的开发者会怎么做？他会先把功能拆成模块：导入、时间轴、裁剪、导出。然后想清楚每个模块的实现逻辑。最后再挨个告诉 Agent，一步一步来。

我一直很困惑要怎么去描述小白和开发之间的能力 gap？

后来我和几个独立开发者聊，他们提到了一个词，叫"技术视野"。

就是你在动手之前，脑子里已经有一个大致的技术地图，知道事情可以怎么拆、先做什么后做什么、哪些地方容易出问题。

这是靠一行一行写代码、一个坑一个坑踩出来的。

但现在的问题是...对于很多外行来说，可能以后都不需要手搓代码了。

那技术视野怎么培养？

总不能让我们先去写三年代码再来做vibecoding吧。

小白和技术大佬有一个无法逾越的能力鸿沟

缩小这个鸿沟可能会有一种新的培养方式，这一方式会是未来软件工程培养人才的通用方式。

技术还在发展，布局尚未定型，没有人能说有通用的方式来培养AI 时代的工程师。

但是每个人是可以结合自己的视野来总结方法。

比如我就可以从产品、运营，外加一点浅浅的开发经验出发

聊聊怎么在 vibecoding 时代培养工程化思维。

不管你是做 Skill、做产品、还是做内容，这几种思维方式其实就是最大限度的挖掘 AI 的能力，什么场景都用得上。

01 先总结下

这六种思维大概是什么，有啥作用，后面再详细展开。

这几个思维都是在回答一个问题：你在让 AI 动手之前，脑子里要先过一遍什么。

1 用户流程与场景：想清楚给谁用、怎么用。这是地基，地基歪了后面全歪。

2 视觉设计：定调性。一句话说清楚"像谁"，需要我们知道一些设计风格。

**3 界面设计：**放什么信息、放哪里。核心原则就一条：用户三次点击内能到达任何地方。

4 交互设计：动起来之后会发生什么。按钮不是只有"能点"和"不能点"两种状态，一个列表也不是只有"有数据"和"没数据"两种样子。

5 数据逻辑：界面背后的水管怎么接。这玩意最容易被忽略，但它决定产品是能跑的 demo 还是能交付的产品。

6 运营设计：上线之后怎么增长。不想清楚增长和变现，做出来的就是个人玩具。

我把这六个思维做成了 skill，如果你不想看下面详解的，可以直接用这个 skill，每次你想要做什么产品，都可以描述：我要做个 xx 产品，大概 xxx，然后就调用这个 skill 输出六个角度的补充信息。

02 六大思维

1

核心问题：谁、在什么情况下、完成什么任务。

想清楚三层：

  • 用户画像：用的人是谁？技术水平怎样？（决定界面复杂度的上限）
  • 任务流程：主线任务是什么（每次打开都要做的），支线任务是什么（偶尔才做的）？主线决定首页放什么，支线决定什么能藏进二级菜单。
  • 场景上下文：用户是从哪里进来的？第一次来还是老用户回访？

描述模板：

目标用户是 [角色]，主要在 [场景] 下使用。核心任务是 [步骤1] → [步骤2] → [步骤3]。入口有 [几种情况]，分别对应 [不同的落地页]。

2

核心问题：产品的整体观感和调性。

很多人以为视觉就是选颜色，其实要想的是这几层：

  • 调性定位：专业严肃？轻松活泼？极简高效？温暖亲切？调性决定配色、字体、圆角、留白这些具体参数。
  • 色彩体系：主色、辅助色、中性色、语义色（成功绿/警告黄/错误红）。一个常见错误是用太多颜色，导致界面杂乱。
  • 设计语言参照：最高效的方式是直接告诉 Agent 参照谁：「参考 Ant Design」「类似 Apple HIG」「Material Design 3」。一句话比你写一百字的颜色描述都管用。

描述模板：

风格 [调性关键词]，主色 [色值]，参考 [某设计体系] 的视觉语言。[浅色/深色] 主题，圆角 [大/中/小]。

3

核心问题：每个页面放什么、怎么排。

视觉管「好不好看」，界面管「放什么、放哪里」。

  • 信息架构：顶层导航有几个入口？层级多深？一个实用原则是「三次点击到达任何地方」。
  • 页面布局：固定宽度还是自适应？单栏/双栏/三栏？有没有固定头部或侧边栏？
  • 组件选型：一组选项用下拉框还是标签切换？列表用表格还是卡片？详情用新页面还是侧边抽屉？每个选择背后都有取舍。
  • 响应式策略：手机上侧边栏变汉堡菜单还是底部 Tab？表格怎么处理？

描述模板：

页面 [名称]：顶部 [导航]，左侧 [侧边栏]，主内容区 [布局+模块]。列表用 [表格/卡片]。移动端 [适配策略]。

4

核心问题：动起来之后会发生什么。

界面管静态截图，交互管动态反馈。

  • 操作反馈：点击后按钮变灰还是出进度条？失败了怎么告诉用户？
  • 状态流转：一个按钮至少有五种状态（默认/悬停/按下/禁用/加载中），一个列表有五种状态（加载中/有数据/空/失败/下拉刷新）。描述得越完整，原型越接近可交付。
  • 手势与快捷操作：移动端的滑动删除、下拉刷新、长按菜单；桌面端的快捷键、右键、拖拽。这些不说 Agent 一般不会主动加。
  • 过渡动画：动画是帮用户理解「从哪来，到哪去」。

描述模板：

点击 [元素] 后 [具体反馈]。异常时 [处理方式]。列表支持 [下拉刷新/分页]。空状态展示 [内容+引导]。

5

核心问题：界面背后的数据从哪来、往哪去。

这是最容易被忽略的维度，但恰恰决定产品能不能真正落地。

  • 数据模型：产品有哪些核心实体（用户、订单、商品），每个实体有什么字段，实体之间什么关系。关系决定页面上能展示什么。
  • API 设计：页面要调哪些接口？一次加载还是分页？筛选排序前端做还是后端做？
  • 数据流向：哪些是全局数据（登录态、购物车），哪些是局部的？A 页面操作后 B 页面要不要同步更新？
  • 缓存与离线：断网了能不能看之前的内容？对移动端尤其重要。

描述模板：

核心实体：[实体名] 包含 [字段]，与 [其他实体] 是 [关系]。页面需要接口 GET /api/xxx，返回 [数据结构]。用户操作后 POST /api/xxx。

6

核心问题：产品上线后怎么转起来。

很多人做原型只想「功能」，不想「运营」，结果做出来的产品没有增长引擎、没有变现路径。

  • 内容运营：内容是 UGC、PGC 还是算法聚合？UGC 要设计发布流程、审核机制、激励体系；PGC 要设计管理后台。
  • 增长机制：邀请有没有奖励？新手任务？沉默用户怎么召回？这些东西对应的是邀请码页、任务清单、Push 落地页。
  • 商业化设计：会员制？广告？抽佣？会员制意味着定价页、开通流程、权益对比表。广告意味着界面要预留广告位。后期才想会改动界面结构。
  • 数据埋点：追踪哪些行为来验证假设。让 Agent 顺手输出一份埋点方案，标注在原型每个关键操作上。

描述模板：

需要运营后台，包含 [模块]。增长路径：[拉新] → [激活] → [留存]。变现模式 [模式]，对应 [页面]。关键埋点 [核心事件]。

03 六个 vibecoding 的切入角度

六个维度是要想清楚问题是什么。

而切入角度是结合上面的六种思维，从哪个角度先来制作这个产品。比如可以先描述框架、或描述用户旅程、或描述组件。

  • 框架驱动（Top-Down） 先定义全局框架（Header、Sidebar、Main Content），再往里填组件。适合仪表盘、内容展示类产品。Agent 的注意力会集中在全局排版和网格系统上。
  • 组件驱动（Bottom-Up） 先把最核心的原子组件（比如一个复杂的 Prompt 编辑器或 AI 对话气泡）调到完美，再让 Agent 围绕这个核心组件生成外围容器。适合强交互的效率工具。
  • 用户旅程驱动（Journey-Driven） 先画出用户从「进来」到「完成目标」的完整链路，每一步就是一个页面。适合流程型产品，比如电商下单、注册引导、审批流。你不是在设计一个页面，是在设计一条路径。
  • 状态机驱动（State-Driven） 先定义所有状态（订单的「待支付/已支付/配送中/已完成/已取消/退款中」），再告诉 Agent 每种状态下界面怎么变。适合工单、订单、审核后台。这种方式天然覆盖交互和数据逻辑。
  • 数据模型驱动（Data-Model-Driven） 先定义数据结构，界面几乎自动推导：字段类型决定表单控件，字段数量决定布局。适合 CRM、ERP、后台管理系统。这是最接近真实开发思维的方式，Agent 可以同时输出原型和 API 结构。
  • 角色权限驱动（Role-Based） 以角色为单位展开描述：管理员看到什么、普通用户看到什么、访客看到什么。适合多角色 SaaS 平台。角色划分本身就是运营策略的体现。

实际做产品时，这些角度经常是混用的。但每次起手的时候，先选一个主角度切进去，思路会清晰很多。
