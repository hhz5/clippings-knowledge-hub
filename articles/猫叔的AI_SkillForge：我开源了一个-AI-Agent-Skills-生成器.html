为什么要做这个

很多人其实并不了解 skills 是啥玩意，所以更多的都是直接用别人推荐的，或者用 find-skills 之类的自动寻找，但这世界上有很多事没有人把它写成skills，你找也是徒劳，那能不能AI自己生成呢？

听起来很美好，但用了多个声称可以完美生成skills的服务： 质量参差不齐。

有的 Skill 看起来格式规范、内容详实，但实际使用时根本无法被正确触发。有的 Skill 把 AI 本来就知道的常识写了一大堆，真正需要的领域知识反而没有。还有的 Skill 动辄上千行，把应该放在参考文档里的内容全塞进了主文件。

问题出在哪？出在 AI 模型并不天然理解"什么是一个好的 Skill"。它知道 Markdown 格式，知道 YAML frontmatter，但它不知道 description 字段其实是一个"触发器"，不知道 SKILL.md 应该只包含 AI 不知道的知识增量，不知道渐进式披露的分层策略。

所以我做了一件事：系统性地分析了 Anthropic 官方 17 个 Skills 的实现、100 多个社区优秀 Skills、以及 Agent Skills 开放标准规范，把"好 Skill"的共性提炼成了一套可复现的方法论，然后把它工程化成了一个 Web 应用。

7 步锻造流程

SkillForge 的核心是一个 7 步生成引擎。每一步都有明确的输入、输出和质量约束，不是简单的"帮我写个 Skill"，而是一个有纪律的锻造过程。

Step 1：需求深度挖掘。 不是直接开始写，而是先用 5 维框架分析需求——核心定位、功能边界、使用场景、知识缺口、依赖约束。其中"知识缺口分析"是最关键的一步：明确区分 AI 已经知道什么、不知道什么、容易犯什么错。这直接决定了 SKILL.md 应该写什么、不应该写什么。

Step 2：架构决策引擎。 做出 5 个关键决策——结构模式（工作流型还是指南型）、自由度级别、资源文件规划、渐进式披露策略、质量保证方案。这一步相当于画建筑图纸，后面的生成都在这个框架内进行。

Step 3：元数据精炼。 生成 3 个候选 description，从触发精准度、能力覆盖度、信息密度三个维度自评打分，选出最优的那个。description 是 Skill 的"触发器"，写得好不好直接决定 Skill 能不能被正确匹配到。

Step 4：SKILL.md 主体生成。 按照 Step 2 的架构决策，生成 150-450 行的精炼指令主体。全程祈使语气，代码示例优先于文字说明，必须包含反面案例。

Step 5：质量审计与优化。 这是整个流程的质量关卡。10 个维度逐项打分，低于 8 分的维度自动修复，然后输出优化后的完整 SKILL.md。

Step 6：配套资源生成。 根据 Step 2 的规划，生成 scripts/、references/、templates/ 等配套文件。每个文件完整可用，没有占位符。

Step 7：最终组装与交付。 格式验证、内容验证、最佳实践验证，三重检查后打包交付。

不只是提示词，是一个完整的工程

😼

你可能会想：这不就是一套提示词吗？

是，也不是。

提示词是核心，但光有提示词还不够。SkillForge 是一个完整的 Web 应用，解决了从"有提示词"到"能用起来"之间的所有工程问题：

上下文管理。 7 步流程中，每一步都需要前面步骤的输出作为上下文。手动操作时你需要不断复制粘贴，而且容易丢失关键信息。SkillForge 自动管理上下文传递，确保每一步都能看到它需要的信息。

结果提取。 LLM 的输出是自由文本，从中准确提取 SKILL.md、资源文件等结构化内容并不简单。SkillForge 内置了多策略提取引擎，通过 YAML frontmatter 验证、PART B 标记定位、内容校验等手段，确保提取的准确性。

任务控制。 7 步流程需要多次 LLM 调用，可能需要几分钟。SkillForge 支持实时进度展示、任务取消、失败重试、历史记录管理。

一键打包。 生成完成后，SKILL.md + 所有资源文件自动打包成 ZIP，下载后直接放到 ~/.claude/skills/ 目录即可使用。

技术栈和部署

SkillForge 的技术栈是 React 19 + Express 4 + tRPC 11 + MySQL，前后端类型安全，开发体验很好。

LLM 调用使用 OpenAI-compatible API 格式，意味着你可以接入任何兼容的提供商——OpenAI、DeepSeek、Together AI，甚至本地部署的 Ollama。只需要在环境变量中配置 API URL 和 Key 即可。

部署很简单：

git clone https://github.com/mmlong818/skillforge.git
cd skillforge/webapp
pnpm install
cp .env.example .env  # 编辑填入数据库和 API Key
pnpm build && node dist/index.js

仓库里有完整的 .env.example 和数据库迁移文件，照着做就行。

一些设计决策的思考

为什么是 7 步而不是 1 步？ 因为"一步到位"的 Skill 生成质量不可控。把流程拆成 7 步，每一步有明确的质量约束和验证点，最终产出的质量远高于一次性生成。这和软件工程中"分阶段交付"的思路是一样的。

为什么要做知识缺口分析？ 这是我在分析大量 Skill 后发现的最关键洞察。大部分低质量 Skill 的通病是：把 AI 已经知道的常识写了一大堆（比如"Python 是一种编程语言"），真正需要的领域知识（比如某个 API 的特殊参数格式）反而没有。知识缺口分析强制 AI 先想清楚"什么该写、什么不该写"。

为什么 description 要自评打分？ 因为 description 是 Skill 的触发器，是整个 Skill 最重要的 30-80 个词。通过生成 3 个候选并从多维度打分，能显著提高触发精准度。
