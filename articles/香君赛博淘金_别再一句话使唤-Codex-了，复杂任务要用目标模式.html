你应该遇到过这种情况。

让 Codex 修一个 bug，它修到一半开始顺手重构；让它补测试，它写着写着忘了验收标准；让它整理一段代码，最后改出来的东西看着很完整，但不是你真正要的结果。

这类问题不一定是 Codex 不够聪明。

很多时候，是你给它的任务太像一句临时指令了。

普通聊天适合短问题，比如解释一段代码、问一个命令、生成一个小函数。但如果任务要连续推进十几分钟，甚至更久，只靠一来一回的聊天就很容易散。

这时候就该用 Codex App 的 Goal mode（填一下昨天留的坑 Codex 这次更新，有点像给 AI 配了一台电脑 ），中文可以直接叫目标模式。

它不是让 AI 变成全自动工程师，而是给 Codex 一张更清楚的任务卡：这次要做什么，边界在哪里，做到什么程度才算完成。

目标模式到底解决什么问题

目标模式的核心很简单：给 Codex 一个可以持续围绕的目标。

这个目标不是一句随口的 prompt。它同时承担两件事：

  1. 它是 Codex 开始工作的起始提示。
  2. 它也是 Codex 判断任务是否完成的验收标准。

比如你平时可能会这样写：

帮我修一下登录失败的问题。

这句话太稀松平常了。

Codex 不知道问题范围、不知道哪些文件能动、不知道什么叫修好，也不知道最后要不要补测试。

在目标模式里，更好的写法应该是：

修复登录页在 token 过期后无法重新登录的问题。

范围：只修改认证流程、登录页逻辑和相关测试，不重构路由，不调整页面样式。

完成标准：token 过期后用户可以重新登录；登录失败时显示明确错误；登录成功后跳转回原页面；不影响首次登录流程。

验证方式：补充或更新相关测试，运行现有测试，并总结改动文件和测试结果。

这就不是一句求助了，而是一个可以执行、可以检查、可以收尾的小任务。

目标模式真正有用的地方就在这里：它不是让 Codex 更自由，而是让 Codex 更不容易跑偏。

什么时候应该用目标模式

不是所有事情都要开目标模式。

如果你只是问一个概念、查一个命令、改一小段代码，普通对话就够了。

当任务出现下面这些特征，就建议切到 /goal ：

  1. 任务需要连续做三五步以上。
  2. 中途可能要读文件、改代码、跑测试、再根据结果调整。
  3. 你希望 Codex 一直记住最终目标。
  4. 你需要明确的完成标准。
  5. 你不希望一个临时追问把主任务打断。
  6. 任务最后需要交付总结、验证结果或修改清单。

适合目标模式的任务，大概是这些：

  1. 修复一个线上 bug，并补回归测试。
  2. 把一个页面从旧 API 迁移到新 API。
  3. 给已有模块补 TypeScript 类型。
  4. 整理一组 lint 或 test 报错。
  5. 重构某个服务模块，但保持外部行为不变。
  6. 先读项目，再提出计划，然后执行其中一个明确改动。

它们都有一个共同点：不是一句问答能结束，需要持续推进，也需要最后验收。

第一步：打开 /goal

在 IDE extension 或 CLI 里，都可以用同一个入口：

/goal

输入 /goal 之后，把你的目标写进去。

如果你输入以后没有看到相关命令，不要先怀疑自己用错了，大概率是 goals 功能还没启用。

可以在 config.toml 里打开：

[features]
goals = true

也可以直接运行：

codex features enable goals

开启后，再回到 IDE extension 或 CLI，用 /goal 创建目标。

Codex App里面则是点击左下角的加号找到追求目标选项

在 Codex App 里，目标启动后，进度会显示在输入框上方。

在cli你可以看到当前目标状态，也可以对目标做几个操作：

  1. pause：暂停目标。
  2. resume：继续目标。
  3. edit：编辑目标。
  4. clear：清除目标。

这几个按钮比看起来重要。

目标跑偏了，不要硬聊，先 pause，再 edit。目标已经完成了，就 clear 掉，避免后面的对话继续被旧目标影响。你要离开电脑、网络不稳、需要人工检查，也可以先 pause，回来再 resume。

一个好目标怎么写

目标模式好不好用，关键不在 /goal 这个命令，而在你写进去的目标质量。

一个好目标至少包含四样东西。

1. 具体结果

不要写：

帮我优化这个项目。

这句话太大，也没法验收。

可以改成：

优化用户设置页的保存逻辑，让保存成功、保存失败、刷新后回显三个流程都可正常工作。

结果越具体，Codex 越不容易自己脑补。

2. 任务范围

告诉它哪些能改，哪些不要动。

比如：

只修改 src/settings 目录和相关测试文件，不调整全局路由，不重构公共组件，不改视觉样式。

很多 AI 写代码的问题，不是不会改，而是太积极。

范围写清楚，就是给它上护栏。

3. 完成标准

告诉它做到什么程度算完成。

比如：

保存成功后展示成功提示；保存失败时保留用户输入并显示错误；刷新页面后能看到最新设置。

没有完成标准，Codex 只能按自己的理解收尾。

有完成标准，它才知道什么时候该停，什么时候还没做完。

4. 验证方式

代码任务一定要写验证方式。

比如：

补充或更新相关测试；最后运行 npm test 和 npm run lint。如果测试无法运行，说明原因和下一步建议。

Codex 可能会说完成了，但你不能只听它说。

把验证方式写进目标里，最后再自己检查一遍，才是比较稳的用法。

可以直接复制的目标模板

你可以先用这个模板：

/goal

目标：完成【一个明确任务】。

背景：【当前问题、业务背景、已知现象】。

范围：
- 可以修改：【允许修改的目录、文件或模块】
- 不要修改：【不希望动的部分】

完成标准：
- 【标准 1】
- 【标准 2】
- 【标准 3】

验证方式：
- 运行【测试命令】
- 检查【页面、接口、日志或行为】

输出要求：
- 总结改动内容
- 列出修改过的文件
- 说明测试结果
- 如果有未解决问题，明确指出

再给一个实际例子：

/goal

目标：修复登录页在 token 过期后无法重新登录的问题。

背景：用户登录一段时间后 token 过期，点击登录按钮会短暂 loading，但页面没有跳转，也没有错误提示。

范围：
- 可以修改认证流程、登录页逻辑和相关测试
- 不要重构整体路由
- 不要调整页面视觉样式

完成标准：
- token 过期后，用户可以重新输入账号密码登录
- 登录失败时显示明确错误提示
- 登录成功后跳转到原本要访问的页面
- 不影响正常首次登录流程

验证方式：
- 补充或更新相关测试
- 运行现有测试
- 如果测试无法运行，说明原因

输出要求：
- 总结问题原因
- 说明具体改动
- 列出修改文件
- 给出验证结果

这类目标比一句修一下登录问题要稳得多。

目标还没想清楚，先别急着开 /goal

很多人第一次用目标模式，最容易卡在这里：我知道自己想让 Codex 帮忙，但我说不清目标。

这个时候不要硬写一个模糊目标。

先用 /plan 。

比如你可以写：

/plan

我想把用户设置页迁移到新 API，但还没想清楚具体步骤。请先帮我拆解任务，列出需要确认的问题、可能涉及的文件、风险点和测试方案。先不要修改代码。

等 Codex 把任务拆清楚，你再把计划整理成 /goal 。

还有一种办法，是让 Codex 先采访你：

/goal

我想完成一个代码修改任务，但目标还不清楚。请先问我 5 个必要问题，帮助我明确任务范围、完成标准和测试方式。在我回答之前，不要修改代码。

它通常会问你：

  1. 最终想解决什么问题？
  2. 哪些文件或模块可以改？
  3. 有没有不能动的部分？
  4. 怎么判断完成？
  5. 需要跑哪些测试？

你回答完，再让它整理成正式目标。

比起憋一个含糊的 prompt，这种方式更适合真实开发。

运行过程中怎么控制它

目标启动后，不是你只能等它跑完。

你仍然可以继续补充要求。

比如：

不要改公共 Button 组件，只在当前页面处理。

或者：

测试先覆盖失败提示和成功跳转，样式细节不用动。

这些 follow-up 可以用来校准方向。

如果你只是想问进度、问原因、问风险，尽量用 side chat，不要打断主任务。

适合问这些：

当前目标进度到哪了？

这次改动的主要风险是什么？

为什么选择改 service 层，而不是页面组件？

还剩哪些验证没做？

这样你可以理解它在做什么，但不会轻易把主线带偏。

常见问题

目标写错了怎么办

不要一路补丁式解释。

直接用 edit，把目标改清楚。

尤其是范围和完成标准，最好一次性写明白。

Codex 跑偏了怎么办

先 pause。

然后检查它为什么跑偏：是目标太大，范围没写清楚，还是完成标准不明确。

改完目标以后再 resume。

如果方向已经完全变了，建议 clear 掉旧目标，重新开一个。

网络不稳定或要离开电脑怎么办

不要让长任务硬挂着。

先 pause，等你回来或者连接稳定后再 resume。

目标完成后还要做什么

至少检查四件事：

  1. diff 是否符合目标范围。
  2. 是否改了不该改的文件。
  3. 测试是否真的跑过。
  4. 结果是否满足完成标准。

如果 Codex 说测试通过，你也最好自己再跑一遍关键命令。

目标模式能让任务更连贯，但不会替你承担最终责任。

我建议你从一个小任务开始练

第一次用 Goal mode，不要从大项目重构开始。

找一个真实但边界清楚的小任务：

  1. 修一个 bug。
  2. 补一个测试。
  3. 给一个页面接入新接口。
  4. 清理一组 lint 报错。
  5. 给一个函数补类型。

先跑一次完整流程：写目标、看计划、补约束、检查结果、自己验收。

跑完你会明显感觉到，它和普通聊天不一样。

普通聊天像你随口叫同事帮忙看一眼。

目标模式更像你发了一张任务卡：做什么、别做什么、做到什么程度算完成，最后怎么验收。

这才是 Codex App 目标模式最值得用的地方。

它不会让 AI 突然变成全自动工程师，但它能把一次长任务协作变得更稳、更可控。

如果你不知道自己的开发任务该怎么写成 Goal，可以在评论区丢一个真实任务。我挑几个改成可以直接复制的目标模板。
