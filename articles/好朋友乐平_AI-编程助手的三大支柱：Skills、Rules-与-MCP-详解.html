AI 编程助手的三大支柱：Skills、Rules 与 MCP 详解

好朋友乐平 2026-03-09

如果你正在使用 AI 编程工具，可能会被各种术语搞得晕头转向：Rules、Skills、Commands、MC

原创 好朋友乐平 2026年3月9日 08:01

如果你正在使用 AI 编程工具，可能会被各种术语搞得晕头转向：Rules、Skills、Commands、MCP、Hooks……每个工具都有自己的术语体系,但核心困惑始终存在。

本文将帮助你理清这些概念,特别是三个最核心的部分： Skills（技能） 、 Rules（规则） 和 MCP（模型上下文协议） 。理解它们的区别,就像掌握了 AI 编程助手的操作系统。

核心心智模型

在深入细节之前,先建立一个简单的类比。如果把 AI Agent 比作一位厨师:

  • MCP Tools = 食材 🥔🥩（原料能力）
  • Skills = 菜谱 📝📇（烹饪方法）
  • Rules = 厨房守则 ⚠️（必须遵守的规则）
  • AI Agent = 厨师 👨🍳（执行者）

这个类比贯穿整篇文章,帮助你直观理解每个概念的作用。

Rules（规则）：不可协商的约束

什么是 Rules？

Rules 是 持久性约束条件,无论执行什么任务都必须遵守。它们定义了"什么必须始终为真",而不是"如何完成任务"。

类比 ：厨房守则

  • 生食熟食必须分开
  • 过期食材不能使用
  • 操作台必须保持清洁

这些规则 无论做什么菜都要遵守,不是针对某道菜的做法。

适用场景

Rules 适合定义 不变量 ：

# 项目 Rules 示例

## 架构约束
- 验证逻辑必须在领域层
- 不得引入新的依赖项
- 公共 API 行为不得在未明确指示的情况下改变

## 代码规范  
- 禁止提交 .env 文件
- 使用设计系统中的 token,不使用硬编码像素值
- 所有 UI 组件必须支持键盘导航

## 测试要求
- 必须复用现有的测试辅助函数
- 修改计费代码时运行集成测试
- 测试必须保持通过

关键特征

特征 说明
触发方式 工具自动应用
作用范围 所有任务
上下文成本 始终占用
稳定性 长期不变

常见误区

❌ 错误 ：把规则当作行为指导

# 不好的 Rule
- 编写整洁的代码
- 重构时要仔细思考
- 适当时进行优化

这些需要"判断"的指令不是约束条件。

✅ 正确 ：定义明确的边界

# 好的 Rule  
- 不得修改 src/legacy/ 目录下的文件
- API 响应格式必须符合 OpenAPI 规范
- 所有数据库查询必须使用预编译语句

Skills（技能）：可选的专业知识

什么是 Skills？

Skills 是 可重用的方法论包,教会 Agent 如何解决特定类别的问题。它们按需加载,只在相关时才被使用。

类比 ：菜谱卡片

  • 意大利面的做法
  • 烤蛋糕的步骤
  • 炖汤的技巧

菜谱不会自己种番茄或磨小麦,但它会 编排如何使用这些食材 。

工作原理：渐进式披露

Skills 的巧妙之处在于"渐进式披露"（Progressive Disclosure）：

Agent 启动
  ↓
扫描 Skills 的名称和描述
  ↓
只在任务相关时加载完整内容
  ↓  
执行 Skill 中的步骤

这就像"懒加载"——Agent 不会一开始就读取所有 Skills,而是需要时才加载,节省上下文空间 。

Skill 文件结构

.cursor/
└── skills/
    └── ui-change/
        ├── SKILL.md          # 主定义文件
        ├── scripts/          # 可执行脚本
        │   └── validate.sh
        ├── references/       # 参考文档
        │   └── design-tokens.md
        └── assets/           # 模板资源
            └── component-template.tsx

实际示例

---
name: ui-change
description: 修改 UI 组件、样式、布局或交互行为时使用此技能
---

# UI 变更技能

## 约束条件
- 使用现有的设计 token 和组件
- 不使用魔法数字或原始像素值
- 保持可访问性：键盘、标签、焦点、对比度

## 工作流程
1. 用一句话重述变更内容
2. 识别最接近的现有组件模式  
3. 实施最小差异的变更
4. 验证响应式行为、焦点状态和键盘导航
5. 有歧义时停下来询问确认

## 成功标准
- ✅ 未使用新 token、魔法数字或原始像素值
- ✅ 在移动/平板/桌面视口上均正常工作
- ✅ 完全支持无鼠标和屏幕阅读器使用

关键特征

特征 说明
触发方式 Agent 根据相关性决定
作用范围 特定任务类别
上下文成本 仅在需要时占用
可操作性 可包含脚本、模板

常见误区

❌ 过早创建 Skill

如果某个流程只做过一次,不要急于创建 Skill。 只有重复出现的模式才值得封装 。

❌ 把 Rule 写成 Skill

# 这应该是 Rule,不是 Skill
---
name: never-commit-secrets
description: 确保不提交敏感信息
---

❌ Skill 过于臃肿

如果 Skill 读起来像百科全书,应该拆分成更小的文件,通过引用链接按需加载。

MCP（模型上下文协议）：连接真实世界

什么是 MCP？

MCP（Model Context Protocol）是一个 开放协议,让 AI Agent 能够调用外部工具、系统和数据源。

类比 ：食材本身

  • 面粉（数据库查询工具）
  • 鸡蛋（API 调用工具）
  • 盐（测试运行工具）
  • 橄榄油（浏览器交互工具）

这些是 原子化的能力,本身没有行为逻辑,但可以被组合使用。

MCP Tools 的特点

特点 说明
原子性 每个工具只做一件事
无状态 通常不保持状态
可组合 可以被 Skills 编排使用
由平台提供 通常由框架/服务提供

实际示例

// MCP Tools 示例
{
"tools": [
    {
"name": "run_tests",
"description": "运行指定的测试套件",
"parameters": {
"test_path": "string",
"coverage": "boolean"
      }
    },
    {
"name": "query_database",  
"description": "执行数据库查询",
"parameters": {
"sql": "string",
"readonly": "boolean"
      }
    },
    {
"name": "browser_click",
"description": "点击浏览器中的元素",
"parameters": {
"selector": "string"
      }
    }
  ]
}

MCP 的作用

MCP 不会提升推理能力,它 提升反馈能力 ：

  • ❌ 不会让 Agent 更聪明
  • ✅ 让 Agent 能验证假设
  • ✅ 让 Agent 能观察真实结果
  • ✅ 让 Agent 能与外部系统交互

常见误区

❌ 把 MCP 当作智能

MCP Tools 只是能力接口,不包含决策逻辑。决策应该在 Skills 或 Agent 层面。

❌ 混淆 MCP Tools 和 Skills

错误理解：
MCPTool="部署应用"

正确理解：
MCPTools= ["运行脚本", "检查状态", "发送通知"]  
  Skill = "部署应用"（编排多个 MCP Tools）

三者对比：决策树

需要添加一个指令？
  │
  ├─ 是否无论何时都必须遵守？
  │    └─ 是 → Rules
  │
  ├─ 是否是特定任务的重复流程？
  │    └─ 是 → Skills
  │
  ├─ 是否需要调用外部系统？
  │    └─ 是 → MCP Tools
  │
  └─ 一次性指令？
       └─ 直接在对话中说明

对比表格

维度 Rules Skills MCP Tools
抽象层次 约束 方法论 能力
触发方式 自动应用 Agent 判断 被调用
作用范围 全局 特定任务类别 原子操作
上下文成本 始终占用 按需占用 调用时占用
可操作性 否 可包含脚本 直接执行
所有权 开发者定义 开发者定义 平台提供
稳定性 长期不变 经常演化 相对稳定
类比 厨房守则 菜谱 食材

组合使用：完整的工作流

最强大的模式是 组合使用 这三者：

示例：实现发布流程

# Rule（约束）
- 发布前必须通过所有测试
- 不得直接推送到 main 分支
- Changelog 必须更新

# Skill（方法）
---
name: release  
description: 执行应用发布流程
---

## 发布流程
1. 检查当前分支是否干净（使用 git_status MCP Tool）
2. 运行测试套件（使用 run_tests MCP Tool）
3. 更新版本号
4. 生成 Changelog（参考 references/changelog-template.md）
5. 创建 Pull Request（使用 create_pr MCP Tool）
6. 等待审核通过

## 成功标准
- ✅ 所有测试通过
- ✅ Changelog 包含所有变更
- ✅ PR 包含正确的标签

# MCP Tools（能力）
- git_status: 检查 Git 状态
- run_tests: 运行测试
- create_pr: 创建 Pull Request  
- send_notification: 发送通知

在这个流程中：

  • Rules 定义了不可违反的边界
  • Skill 编排了具体的执行步骤
  • MCP Tools 提供了实际操作能力

实用建议

1. 保持 Rules 简短

Rules 应该只包含 路由逻辑 ：

# 好的 Rule
- 修改 UI 组件时，加载 ui-change Skill
- 调试生产错误时，加载 incident-triage Skill
- 操作计费代码时，加载 billing-safety Skill

2. Skills 的黄金法则

每个 Skill 必须回答六个问题：

  1. 触发条件 （Description）：何时加载？
  2. 输入 ：需要什么信息？
  3. 步骤 ：执行流程是什么？
  4. 检查 ：如何验证成功？
  5. 停止条件 ：何时需要人工介入？
  6. 恢复 ：检查失败时怎么办？

3. 基础 Skill 库

建议从这些 Skills 开始：

  • repo-orientation : 仓库结构和约定
  • ui-change : UI 组件修改流程
  • debugging : 问题复现和日志分析
  • verification : 变更验证命令
  • pr-hygiene : 提交信息和 Changelog
  • safety : 安全边界

4. 先用 Skills，再考虑其他

遇到问题时的优先级：

  1. 能用 Skills 解决吗？（大部分情况）
  2. 需要单独的 Sub-agent 吗？（权限隔离）
  3. 需要新的 MCP Tool 吗？（缺少能力）
  4. 需要升级 Rule 吗？（新的约束）

总结

理解 Skills、Rules 和 MCP 的关键在于认识到它们控制的是 AI Agent 工作流的 不同阶段 ：

  • Rules → 定义边界（"什么是不可协商的"）
  • Skills → 提供方法（"如何完成任务"）
  • MCP Tools → 赋予能力（"可以做什么操作"）

就像厨房的类比：

  • Rules 是厨房守则，保证食品安全
  • Skills 是菜谱，指导如何烹饪
  • MCP Tools 是食材和工具，提供原料和手段
  • AI Agent 是厨师，按照菜谱使用食材，遵守厨房守则

当你清楚区分这三者时，AI 编程助手就会从"神秘的黑盒"变成"可理解的协作系统"。新工具不再令人困惑，而是变得可组合、可预测。

最重要的是： 责任仍然在你手中 。Agent 只是执行你设计的系统，代码的正确性、安全性和清晰度，始终由你这位工程师负责。
